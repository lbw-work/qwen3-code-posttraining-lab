# DPO 偏好数据与核心数学复核

## 结论

当前偏好数据存在已确认的质量缺陷和明显的覆盖限制。可以将其作为局部错误辨别训练集，但不应将“原有 10 条测试全部通过”等同于“正例完全正确”，也不宜期待仅用这一种负例构造方式显著提高所有算法题的通过率。

本次没有证明这些缺陷就是 MBPP 回退的原因。需要相同 SFT 起点、独立开发集和控制变量实验才能建立因果证据。

## 检查范围与复现

- 全量：3,212 对训练数据、153 对验证数据，共 3,365 对。
- 检查训练文件、验证文件、provenance 与数据锁哈希；未改变任何冻结数据。
- 全量检查：AST、唯一 token 改动、来源、函数名、重复和 tokenizer 边界。
- 固定种子 20261004 随机抽取 100 对（训练 97、验证 3），在受限 Docker 中重新执行 200 份代码各自的 10 条已有测试。
- Docker 镜像与原始数据构造时的镜像 ID 相同。100 对均复现来源分数；chosen 均 1.0，rejected 均低于 1.0。
- 另做针对性检查，详情见 `supplementary.json`。这些检查不是随机错误率估计。

复跑主体检查（在项目根目录，使用装好项目依赖的 Python）：

```bash
python scripts/audit_dpo_data.py
```

输出目录：`results/analysis/dpo-preference-audit-v1/`。脚本会重写该诊断目录的主体输出；不会重写训练数据、数据锁或模型。针对性检查另存 `supplementary.json`，主体脚本不会重跑该文件中的人工选定断言。

## 具体缺陷

### 1. 正例遗漏明确要求的校验

位置：`data/preference/train.jsonl` 第 1724 行，函数 `generate_robot_property`。

题干要求 `property_value` 必须是整数，否则抛出 `ValueError`。正例只检查 `0 <= property_value <= 100`，没有检查整数类型。

Docker 中新增测试：

```python
try:
    generate_robot_property('arm_length', 5.5)
except ValueError:
    pass
else:
    raise AssertionError('non-integer value must raise ValueError')
```

结果：失败。虽然原有测试能通过，正例仍未满足明确的错误输入处理要求。这不自动说明 rejected 更好，也不证明偏好顺序颠倒；它证明“chosen 完全正确”这一前提不可靠。

### 2. 题干示例自身有错

位置：训练集第 1610 行，函数 `find_smallest_difference_pair`。

输入 `[4, 9, 1, 32, 13, 5]`。题干写 `(4, 5) # or (9, 13)`，但两者差分别是 1 和 4，后者不是最小差答案。

正例在该输入返回 `(4, 5)`，Docker 检查通过。错误存在于题干说明，不能误标为代码错误。涉及“任意顺序/任意合法解”的示例常被保守解析器跳过，原有示例审查无法保证覆盖它们。

### 3. 题干与答案的输入输出协议不统一

位置：训练集第 1095 行，`length_of_lis`；第 2627 行，`search_insert_position`；第 902 行，`transpose_matrix`。

这些题干描述读取标准输入并打印，chosen 却只定义函数、接收参数并返回结果。第 1095 行的核心函数在题干示例对应数组上输出正确，Docker 函数测试通过；作为标准输入程序则没有执行入口。

应明确转换成函数题协议：给出函数签名、参数说明与返回值，并同步转换 chosen、rejected 和测试。不要仅删除题干里的“print”而保留其它输入描述。

## DPO 核心数值对照

参考：DPO 作者仓库 `eric-mitchell/direct-preference-optimization` 的 `trainers.py`，固定提交 `f8b8c0f49dc92a430bae41585f9d467d3618fe2f`。

本次提取作者的 `preference_loss` 与 `_get_batch_logps` 两个实际函数，使用 CPU float32 随机 logits 检查 40 组不同题干/答案长度和右侧 padding。

序列概率误差来自求和路径的浮点舍入，在预设容差内；prompt 和 padding 标签被正确屏蔽。参考源文件及 SHA256 已保存。

局限：这不是实际 Qwen 前向、CUDA/bf16、LoRA 加载、reference 冻结状态或优化器更新的完整验证。不能以数学检查通过宣布整个训练实现无误。

## 与当前评测的关系

已有统一评测中，LoRA SFT → DPO：HumanEval+ 从 82/164 提升到 96/164；MBPP+ 从 237/378 降到 228/378。两个数据集的变化方向不同。

因此，应分别分析算法、题干理解、边界条件和输出协议，而不是把结果归为单一的整体退化。上述缺陷可能限制提升或造成部分题型回退，当前证据不足以计算各项缺陷对通过率的贡献。

## 下一轮实验建议

1. 保留本轮模型、数据锁、结果作为历史基线。创建独立 v3 数据版本。
2. 修正或排除错误题干和不充分验证的正例；加强边界、异常、重复、空输入测试，但只覆盖题干明确允许或要求处理的情况。
3. 统一为 Python 函数题，提供明确签名。按题目或算法家族划分训练与开发集；开发题不进入 SFT、DPO 或奖励模型训练。保持正式 eval 不进入数据构造。
4. 从同一 LoRA SFT 起点，对独立训练题生成多份真实候选，在 Docker 中选取通过与失败答案。负例覆盖选错算法、重复元素处理、类型/返回值、函数名、语法与多余输出；不要只拼接人为错误。
5. 人工单 token 改动作为补充，不作为唯一负例来源。负例已通过大部分测试不必删除；应检查是否确实违反题意、是否有不同难度的负例。
6. 先做 500–1,000 对的小规模对照：A 使用清理后的人工改动；B 使用真实候选偏好。保持样本数、SFT 起点、token 限制、优化步数、学习率、beta 和解码协议一致，并报告 token 量与长度差。
7. 在独立开发集按代码通过率选择 checkpoint，同时记录 preference accuracy、chosen/rejected log probability、相对 reference 的变化与长度。不要仅凭验证 DPO loss 选择模型，也不要用正式 eval 反复调参。
8. 若 B 稳定好于 A，再扩数据并复核；若仍退化，继续核对模型加载、实际 reference、梯度累积和更新幅度。任何方案都不能预先保证显著提升。

PPO 的奖励模型如果沿用同一偏好集，也会受到这些覆盖和验证限制。但本报告没有复核奖励模型或 PPO 的实际训练，因此不把 PPO 回退直接归因于这份数据。
